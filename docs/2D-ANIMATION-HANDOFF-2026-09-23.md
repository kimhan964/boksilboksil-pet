## 1. 사용자 요구와 현재 작업 상태

- 사용자가 확인한 문제: 모션에 따라 동물의 크기와 색깔이 달라지고 전체 완성도가 부족하다.
- 최종 제작 방향: **2D 토끼부터 다시 제작**한다. 사용자가 3D 모델 제작 제안을 명확히 정정했다.
- 제작 도구: **VARCO MCP**. 사용자는 사용량·토큰 절약보다 고품질과 일관성을 우선하도록 요청했다.
- 가장 최근 요청: 제작에 앞서 무엇이 중요한지 분석하고 인수인계서를 작성한다.
- 이번 작업 완료 범위: 코드·원본 이미지·기존 검사 범위 분석, 바르코 연결 및 노드 사양 확인, 제작·통합·검수 기준 문서화.
- 최초 분석 시점에는 이미지 생성·코드 변경이 없었다. 이후 사용자가 제작과 게임 적용을 승인했다. 파츠 방식의 시도는 사용자 지시로 폐기했으며, 새끼/성체별 전신 프레임 생성 및 통합을 진행한다. 최종 적용·검사 결과는 별도 작업 결과 문서에 기록한다.

이 문서의 숫자 중 ‘제안’으로 표시한 값은 앞으로 적용할 검수 기준이다. 현재 결과가 해당 기준을 통과했다는 의미가 아니다.

## 2. 가장 중요한 결론

현재 문제는 이미지 제작과 표시 코드 양쪽에서 발생할 수 있다. 새 원화를 잘 만드는 것과 모든 동작을 같은 좌표·색상·크기 규칙으로 표시하는 것을 함께 해결해야 한다.

우선순위는 다음과 같다.

1. **캐릭터 기준 고정:** 같은 성장 단계의 얼굴·귀·몸 비율, 털색, 목 장식, 선 두께를 하나의 기준 원화에 고정한다.
2. **공통 크기와 좌표:** 모든 프레임에 같은 캔버스, 원점, 제작 배율을 사용한다. 포즈의 바깥 경계 높이로 매번 몸을 확대·축소하지 않는다.
3. **시간에 따른 연속성:** 앞뒤 프레임과 동작 전환을 함께 검수한다. 개별 정지 그림이 예쁜 것만으로 애니메이션 품질을 판단하지 않는다.
4. **색상 관리:** 털·귀 안쪽·볼·장식·외곽선의 팔레트를 부위별로 고정한다. 프롬프트 문구와 생성 모델 이름만으로 일관성을 보장할 수 없다.
5. **실제 크기 검수:** 성체 기준 약 110px, 새끼 시작 약 68.2px의 표시 크기에서 얼굴과 실루엣이 또렷해야 한다. 고해상도 원본만 보고 합격시키지 않는다.
6. **접촉과 상호작용:** 발의 접지, 손과 음식, 입과 먹이 판정, 캐릭터와 소품의 상대 위치가 동작에 맞게 이어져야 한다.

[animation_regions.gd](<C:/Users/rlagk/Documents/바탕화면 친구/scripts/animation_regions.gd:4>)는 manifest의 `body` 사각형 중심 X와 아래쪽 Y를 기준으로 이미지를 공통 캔버스에 배치한다. [build_animation_regions.py](<C:/Users/rlagk/Documents/바탕화면 친구/tools/build_animation_regions.py:36>)에서 일반 시트의 `body`는 주된 연결 영역의 bounding box로 만들어진다.

### 4.4 색상은 공통 팔레트로 관리되지 않는다 — 코드와 이미지 확인

토끼는 기본 Resource, 새끼 기본, 추가 동작, 걷기, 반응, 수면, 들기, 소품 상호작용 등 여러 출처의 그림을 사용한다. 새끼 기본 시트·새끼 걷기 시트·토끼 반응 시트를 직접 확인했다. 원본의 얼굴 구성, 귀 표현, 장식 크기, 채색 방식이 시트마다 다르며, 새끼와 성체의 의도적인 디자인 차이도 포함되어 있다. **성장 차이를 모션 오류와 혼동하지 않고 동일 성장 단계 안에서 비교해야 한다.**

이번 분석에서 토끼의 부위별 색차를 수치 측정하지는 않았다. 사용자가 본 색상 변화의 정확한 범위는 새끼/성체별 실제 출력 프레임을 캡처해 확인해야 한다.

## 6. 고품질 2D 제작 기준

### 캐릭터 기준표

토끼의 현재 정체성인 밝은 크림/아이보리 털, 분홍 귀 안쪽과 볼, 짙은 눈·외곽선, 초록 목 장식을 출발점으로 한다. 과거 바르코의 과장된 마스코트 후보는 별도 후보이며, 현재 게임 디자인의 확정 기준으로 간주하지 않는다.

각 성장 원화에 다음을 기록한다.

- 기준 정면/게임 시점 원화와 파일 해시, 기준 포즈 이름.
- 머리 폭과 높이, 몸통 폭과 길이, 눈 사이 거리, 귀 밑동 위치, 손발 길이의 비율.
- 털 기본색·그림자색, 귀 안쪽, 볼, 목 장식, 외곽선의 sRGB 색상표. 최종 기준 원화에서 채취하고 이후 고정.
- 기본 시점과 좌우 방향 규칙. 좌우 반전 시 비대칭 귀·장식이 어떻게 보일지 결정.
- 외곽선과 내부선 두께, 그림자 단계, 하이라이트 범위. 매 동작마다 광원을 다시 해석하지 않게 한다.
- 새끼와 성체 원화를 구분하되 같은 단계의 모션에는 같은 기준표를 적용. 중간 단계는 현재와 같이 성체 원화의 크기 변화로 시작할 수 있다.

### 좌표·배율 계약

- 원화 원본은 충분한 해상도로 보존하고 실제 출력 프레임은 동일한 크기의 캔버스에 배치한다.
- 모든 포즈에 공통 제작 배율을 사용한다. 프레임별 `used_rect.height`를 표시 배율의 분모로 사용하지 않는다.
- 제작 원점, 발바닥 접지선, 머리 기준점, 입·양손·소품 접점, 몸통 bounds를 메타데이터로 저장한다.
- 귀나 꼬리를 포함한 시각적 bounds는 잘림 검사에 사용한다. 신체 크기 기준은 기준 원화의 몸통·머리 치수에서 정한다.
- 점프에는 의도한 원점 상승량을 남긴다. 수면에는 몸통 크기를 유지한 낮은 자세를 사용한다. 모든 프레임의 발끝을 무조건 같은 위치로 끌어내리지 않는다.
- `FEET=(102,160)`, 창 204×190, 토끼 기본 높이 110의 기존 표시 환경부터 검수한다. 새 캔버스 해상도는 이와 별개의 제작 설정이다.
- 음식·당근·클로버는 가능하면 별도 레이어로 합성하고, 캐릭터 배율 산정에 포함하지 않는다.

예시 메타데이터 구조(새 규격 제안이며 현재 파일 형식이 아님):

```json
{
  "character": "rabbit",
  "stage": "baby",
  "reference_id": "rabbit-baby-master-v1",
  "palette_id": "rabbit-palette-v1",
  "canvas": [512, 512],
  "root": [256, 448],
  "reference_height_px": 352,
  "frames": [
    {
      "file": "idle_000.png",
      "duration_ms": 160,
      "root_offset": [0, 0],
      "mouth": [300, 260],
      "hand_l": [250, 320],
      "hand_r": [310, 320],
      "contacts": ["foot_l", "foot_r"]
    }
  ]
}
```

좌표값은 구조 설명용 예시다. 실제 값은 완성한 기준 원화에서 측정한다.

### 투명 배경과 가장자리

최종 게임용 프레임은 실제 알파 채널이 있는 PNG로 저장하고, 귀·털·외곽선 가장자리를 밝고 어두운 배경에서 모두 확인한다. 체크무늬가 그림에 포함된 이미지는 투명 이미지가 아니다. 바르코가 투명 출력을 지원한다고 가정하지 말고 실제 다운로드 결과를 확인한다.

현재 [keyed_art.gd](<C:/Users/rlagk/Documents/바탕화면 친구/scripts/keyed_art.gd:1>)는 마젠타 계열 배경을 색상 차이로 제거한다. 이 방식은 토끼의 분홍 귀·볼 가장자리와 배경색이 섞인 부분에도 영향을 줄 수 있다. 실제 손상 여부는 별도 확인이 필요하다. 새 투명 PNG를 넣을 때는 기존 배경 제거가 다시 적용되는지 확인하고, 반투명 테두리와 작은 색상 조각이 외곽선·클릭 영역을 부풀리지 않게 검수한다.

## 7. 바르코를 사용하는 제작 절차

### 연결과 지원 기능

이번 MCP 조회에서 대상 워크플로의 연결을 확인했으며 기존 노드는 41개였다. 기존 동물 후보 이미지가 있으므로 새 토끼 작업은 캔버스 오른쪽 등의 별도 영역에 추가한다. 확인한 기존 노드의 최대 오른쪽 끝은 x=5380이다. 배치 후 실제 노드 크기를 조회해 겹치는 부분을 정리한다.

사용할 노드는 `TextInput`, `ImageInput`, `GenerateImage`, `EditImage`다. **2D로 작업하며 Generate3D / Rig / Animate는 사용하지 않는다.** 현재 `Animate`는 3D 뼈대가 있는 모델을 입력받는 노드로, 2D 연속 프레임을 만드는 기능은 아니다.

확인한 이미지 모델 선택지는 `gpt-image-1.5-medium`, `gpt-image-2-medium`, `gpt-image-2.5-flare`, `nano-banana-1`, `nano-banana-2`, `nano-banana-pro`다. 이름만으로 품질 순위를 정하지 않고 기준 원화 재현과 세부 표현으로 비교한다. 이번 계정 조회에서 이미지 생성은 사용 가능했다.

카탈로그에서 지정할 수 있는 이미지 조건은 모델·장수·가로세로 비율이다. 픽셀 해상도·시드·투명 배경·편집 마스크 전용 매개변수는 확인되지 않았다. 지원하지 않는 제어 기능을 사용할 수 있다고 가정하지 않는다.

### 실행 순서

1. **기준 원화를 만든다.** 기존 토끼를 참고해 실제 게임에서 읽기 좋은 얼굴·귀·장식과 선명한 2D 표현으로 정리한다. 새 생성 작업은 사용자가 요청한 범위이며 문서 작성 단계에서는 미실행이다.
2. **기준을 고정한다.** 원화, 팔레트, 신체 비율, 공통 좌표, 성장 단계의 대응을 저장한다.
3. **짧은 시범 모션부터 만든다.** 대기→걷기→대기, 대기→쓰다듬기→대기를 만들고 실제 크기로 연속 비교한다. 이 단계에서 배율·색상이 튀면 먼저 수정한다.
4. **기준 원화를 편집한다.** `EditImage.sourceImage`에 고정한 원화를 전달하고 `referenceText`에 바꿀 자세와 유지할 요소를 적는다. 다른 생성 결과를 임의로 새 기준으로 삼지 않는다.
5. **앞뒤 관계를 보여준다.** 중간 자세는 기준 원화와 시작·종료 자세를 함께 참조한다. 직전 생성 결과만 연속 편집하는 방식은 외형의 오차가 쌓일 수 있으므로 고정 원화를 계속 참조한다.
6. **생성 후 정리한다.** 팔레트, 신체 비율, 원점, 투명 영역, 프레임 순서를 검사하고 벗어난 그림을 수정·재생성한다. 같은 프롬프트·모델·시트에서 나왔다는 이유만으로 합격시키지 않는다.
7. **짧은 모션 단위로 확장한다.** 걷기·식사 등 의미 있는 작은 묶음을 완성하며, 큰 64칸 시트에 모든 것을 한 번에 생성해 품질이 떨어지지 않게 한다. 프레임 하나당 실제 픽셀 수도 확인한다.
8. **결과를 저장한다.** 다운로드에는 `get_output_downloads`를 사용한다. 기준 원화, 채택한 프레임, 생성 원본, 프롬프트, 모델명, 노드ID, 날짜, 참조 이미지ID를 기록한다.

MCP 실행 시 `run_workflow.scope`에 이번 이미지 노드ID만 전달한다. 비어 있는 scope는 기존 전체를 재실행하므로 사용하지 않는다. 생성은 비동기이므로 `get_workflow_graph`로 상태를 확인하고 진행 중인 작업을 중복 시작하지 않는다.

### 프롬프트에 포함할 고정 조건

> 참조 토끼와 같은 캐릭터를 유지한 2D 게임 애니메이션 원화. 지정한 자세와 표정만 바꾼다. 얼굴 윤곽, 머리와 몸통 비율, 눈과 귀 밑동, 털색, 초록 목 장식, 선 두께, 광원과 그림자색을 유지한다. 같은 카메라 거리와 제작 배율, 전신이 들어가는 공통 캔버스를 사용한다. 귀를 접어도 머리나 몸통을 확대하지 않는다. 각 프레임의 동작 순서를 지킨다. 글자, 다른 동물, 불필요한 장식을 추가하지 않는다.

실제 제작에서는 위 조건에 동작별 시작·중간·종료 자세를 추가해 한국어 또는 영어 프롬프트로 정리한다.

## 8. 애니메이션 제작 방식 권고

**확정 방식: 바르코에서 완전한 전신 프레임을 행동별로 생성하고, 게임에서 순서대로 재생한다.**

- 새끼와 성체는 각각 별도 기준 원화·별도 프레임을 사용한다. 성체 그림을 축소한 것만으로 새끼 제작을 완료했다고 하지 않는다.
- 각 행동은 해당 성장 단계의 고정 원화를 직접 참조한다. 직전 생성물을 기준으로 연쇄 편집해 외형이 변하지 않도록 한다.
- 양쪽 눈·귀·팔다리가 얼굴과 몸에 자연스럽게 연결되어 있어야 한다. 눈·얼굴·몸을 따로 만들어 붙이거나 관절별로 회전시키지 않는다.
- 생성 후 허용되는 기술 처리는 배경 제거, 프레임 자르기, 캔버스 정렬, 시퀀스 전체에 동일한 배율 적용, 색상 검수와 필요한 보정이다. 신체 파츠 조립은 허용하지 않는다.
- 시작·종료 자세와 걷기 반복, 앉기·일어서기, 들기·착지의 실제 전신 프레임을 연결한다. 부족하거나 불량한 자세는 이미지 생성으로 다시 만든다.

참고: [Godot의 2D 스프라이트 애니메이션](https://docs.godotengine.org/en/stable/tutorials/2d/2d_sprite_animation.html).

## 9. 토끼 모션 제작 범위와 우선순위

| 순서 | 모션 | 반드시 유지·확인할 것 |
| --- | --- | --- |
| 1 | 대기·호흡·눈깜빡임 | 얼굴 크기 고정, 미세 호흡, 기본 표정 |
| 2 | 걷기·출발·정지 | 같은 머리/몸통, 발 접지, 이동 거리와 보폭, 마지막→첫 프레임 연결 |
| 3 | 쓰다듬기·인사·바라보기 | 귀를 접어도 몸을 키우지 않음, 눈·입 위치 유지 |
| 4 | 먹기·마시기·직접 먹여주기 | 손·입 좌표, 음식 가림 순서, 씹기→삼키기→쉼 |
| 5 | 들기·착지·수면·일어나기 | 지면/공중 원점 구분, 낮아진 자세에서 몸통 크기 유지 |
| 6 | 놀이·킁킁·폴짝·고유 행동·따라오기·부비기 | 준비→행동→정리, 귀·장식의 따라오는 움직임 |
| 7 | 당근 소품·클로버 휴식·반응 8종 | 소품 포함 bounds로 토끼 크기를 바꾸지 않음, 모든 경로 새 원화 연결 |

기존 상태와 보상·해금·저장 로직을 그대로 연결할 수 있도록 모션 이름 대응표를 먼저 만든다. 단순히 FPS를 높이거나 같은 자세를 복제하는 것은 자연스러운 중간 동작을 만드는 작업을 대신하지 못한다. 필요한 실제 자세와 프레임별 유지 시간을 함께 설계한다.

아래 수치는 초기 **제안 기준**이다. 원화 확정 후 측정 방법과 예외를 함께 고정한다.

| 항목 | 검사 방식 / 제안 합격 기준 |

| 기본 배율 | 동일 성장 경험치에서는 모든 모션의 기본 배율 동일. 의도한 squash/stretch는 별도 값으로 기록 |

| 색상 | 동일 신체 부위의 내부 기본색은 같은 팔레트. 색차 측정 시 가장자리·볼·그림자 제외; 중앙값 ΔE00≤2를 초기 목표로 사용 |
| 발 접지 | 정지·지지 구간에서 의도하지 않은 흔들림 실제 표시 크기 기준 1px 이내 목표. 점프·이동은 지정 궤적과 비교 |
| 선·투명도 | 흰색·검정·회색 배경 모두에서 분홍 테두리, 흐릿한 외곽, 잘린 귀·발, 다른 프레임 조각이 없어야 함 |
| 모션 전환 | 대기→걷기→대기, 대기→쓰다듬기→대기, 걷기→식사, 식사→대기, 들기→착지, 수면→기상을 연속 재생 |
| 외형 | 이중 눈·손, 귀 길이 급변, 장식 증발, 털색 점멸, 표정 순간 교체 없음 |
| 창 경계 | 일반 모션 중 보호용 자동 축소가 발생하지 않음. 큰 동작의 여백을 미리 확보 |
| 성장 | 새끼·중간·성체와 경험치 11→12, 35→36 확인. 같은 단계의 모션 변화를 성장으로 오인하지 않음 |
| 조작 | 양방향 보기, 드래그, 클릭 통과, 먹이 판정, 소품 접촉, 화면 경계가 그림과 맞음 |
| 실제 품질 | 현재 크기 1배와 확대 2~4배 모두 확인. 확대 이미지만으로 합격 처리하지 않음 |

검사는 전체 그림 높이 하나로 판단하지 않는다. 중립 포즈의 해부학적 비율, 부위별 색, 예상 루트 이동, 실제 스프라이트 배율을 분리해 기록한다. 전신 프레임에 눈이 사라지거나 팔다리가 변형되는 생성 오류가 없는지 확인한다.

### 기존 검사로 보장되는 범위

- `tools/check_click_size.gd`: 기본 대기와 쓰다듬기의 표시 높이 차이를 검사한다. 16종×3단계×27시점 구조이며 허용 차이는 3%. 다른 모션의 얼굴 비율·색상까지 검사하지 않는다.
- `tools/check_animation_views.gd`: 프레임과 외곽선의 화면 경계 및 일부 성장 원화 경로를 검사한다. 색상 일관성 검사는 아니다.
- `tools/check_package.gd`: 시점 하나에서 16종×3단계×8행동의 텍스처 존재 여부 등을 확인한다. `growth_stage`를 바꾸지만 해당 루프에서 `growth_scale`은 단계별로 설정하지 않는다.
- 보관된 `builds/package-0.28.5-check.log`에는 `PACKAGE_POSES=384 FAILURES=0`이 있다. 2026-09-21의 과거 로그이며 이번 작업에서 재실행한 결과가 아니다.
- `tools/preview_transitions.gd`는 이름과 달리 현재 `m.species=4`인 너구리 비교 코드를 담고 있다. 토끼 검수 시 species와 모션 범위를 바꾸거나 별도 도구를 만들고 출력 이름도 구분한다.

이번에는 소스와 PNG를 정적으로 검토했다. 토끼 전체 모션의 실시간 캡처, 색차·크기 수치 측정, 새 엔진 실행 테스트는 수행하지 않았다. 따라서 위의 위험 조건을 모두 실제 발생한 버그라고 단정하지 않는다.

## 11. 다음 구현자가 지킬 통합 순서

1. 기존 Git 변경 목록, 토끼 에셋·스크립트의 해시와 실행본 버전을 기록한다.
2. 토끼의 동일 성장 단계별 기존 모션을 캡처해 비교 기준을 만든다. `sprite.scale`, `growth_scale`, 사용 텍스처, 외곽선 fit 배율도 기록한다.
3. 토끼 기준 원화를 만들고 비율·색상·좌표표를 확정한 다음 짧은 시범 모션을 생성한다.
4. 새 토끼 전용 에셋 로더와 공통 배율·원점 적용 방식을 마련한다. 사용 중인 시트의 레이아웃과 body bounds를 새 그림에 그대로 재사용하지 않는다.
5. `desktop_pet_view.gd`의 토끼 분기를 연결하고, `stabilize_pet_pose()`와 `Outline.fit()`이 새 기준을 다시 바꾸는지 확인한다. 그림·음식·클릭 외곽선에 동일한 변환을 사용한다.
6. 손·입·소품 좌표를 새 원화에 맞춰 갱신한다. `main.gd`의 현재 입 위치 추정과 실제 새 토끼의 입을 함께 비교한다.
7. 모든 상태가 새 토끼 에셋을 사용하는지 검사한다. 새끼만 바꾸고 성체 또는 소품 행동에서 옛 토끼가 나오는 상태로 완료 처리하지 않는다.
8. 기존 기능 검사와 새 일관성 검수를 수행한다. 다른 동물은 원래 경로를 사용하는지 회귀 확인한다.
9. 검수용 새 버전으로 패키징한다. `tools/package.gd`는 현재 `DesktopFriends-0.28.5-release` 경로가 하드코딩되어 있으므로 그대로 실행하면 기존 출력에 쓸 수 있다. 새 출력 경로를 먼저 정한다.
10. 새 패키지를 실제로 실행해 모션 전환을 확인하고, 사용자의 저장 진행과 기능을 이어받는지 확인한다. 소스만 바꾸고 이전 PCK를 실행한 결과를 완료로 보고하지 않는다.

## 12. 최종 인계해야 할 결과물

- 토끼 성장 단계별 기준 원화와 스타일·색상·좌표표.
- 새 모션 프레임, 프레임별 시간·원점·입·손 좌표, 상태 대응표.
- 바르코 원본 출력과 프롬프트·모델·워크플로/노드ID 기록.
- 공통 배율·원점 적용 코드와 변경 설명.
- 같은 성장 단계의 수정 전/후 비교 이미지 및 연속 재생 영상.
- 실제 수행한 검사 결과와 미검증 항목.
- 새 실행본 경로, 대응 PCK 버전, 원본 복구 방법.

## 13. 다음 작업 시작용 문장

> 이 인수인계서를 기준으로 복슬복슬펫의 모루(토끼)를 바르코 MCP로 고품질 2D 원화와 일관된 애니메이션으로 다시 제작한다. 3D는 사용하지 않는다. 현재 미커밋 변경을 보존하고, 토끼 성장 단계별 기준 원화·팔레트·좌표를 고정한다. 대기·걷기·쓰다듬기의 짧은 시범 동작으로 외형·색·크기 연속성을 먼저 검증한 뒤 모든 상태에 확장한다. 바르코 생성은 이미 요청된 범위이며 사용량 절약보다 품질을 우선한다. 새로운 추가 지시가 있으면 그 지시에 맞춰 진행한다. 모든 프레임을 높이 기준으로 강제 정규화하거나 교차 페이드만으로 동작을 보간하지 않는다. 게임의 공통 배율·앵커·창 맞춤·음식·입 판정까지 확인하고 실제 새 실행본을 검수해 인계한다.
